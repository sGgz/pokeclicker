# 农场满级助手布局计算说明

本目录为攻略文件的计算依据与复核工具，不参与游戏运行。主要交付文件为上一级的 `农场满级助手布局大全.html`；HTML 内嵌全部数据，离线打开后可搜索、查看 5×5 田格，并复制单个方案的完整原生布局 JSON。另提供同名 Markdown 文件，便于检索与版本比较。

## 计算基准

- 规则来源：当前仓库游戏 `0.10.27`，基准提交 `ff4bfecd9`，2026-10-18。
- 单块农田 25 格全部解锁，农场助手全部 Lv.50；并不读取或修改用户真实存档。
- 未获得实际道具倍率前，使用本分支满级并启用的 Sprayduck `2.75×`、Sprinklotad `4.5×`。倍率不同会影响助手巡田的取整结果，不能只将产量按比例换算。
- 树果方案以目标果实库存净新增为目标，忽略工资和肥料支出来选优，但照常计算真实种子、肥料和助手动作。
- 农场币分别比较采收毛收入、扣工资收入、再扣基础价肥料的收入。Boost、Rich、Amaze 基础价分别为 50、100、200 农场币；动态价格采购应替换实际成本。
- 农场币另将毛收入冠军、成熟平台净收入冠军与纯 Wacan/Jamie 方案连续运行 96 小时，跨过 Petaya 的寿命与重建空档。长时推荐仅在这三份对照中选优。
- 光环方案为全部指定树果成熟时的峰值。数学峰值、无寄生替代、Babiri 防护推荐与 Petaya 成熟保活窗口分开标注。

## 优化范围与可信度

生产布局在普通 `cycle` 种收策略内搜索。生产格与 Passho、Wacan、Lum 辅助格参与空间组合，辅助阵一般固定一株位于左上角的 Petaya。对 Enigma、Occa、Kebia、Colbur、Chople、Tamato、Cornn、Magost、Rabuta、Nomel、Spelon、Pamtre、Watmel 采用四株 Babiri 的全场保护模板；四株位置为索引 `6、8、16、18`，对应第 2、4 行的第 2、4 列。保护格必须先成熟，不能冻结。

搜索使用按果实编号固定的伪随机种子、多起点退火和格子交换，比较 Rich、Amaze、Boost，以及按生产格分别选肥的混合方案；同时纳入无辅助全田基线。静态阶段用生产株平均生长期光环粗筛，随后使用当前源码的 `Farming`、`FarmHand`、`FarmLayout`、`Plot` 执行链复核候选。最后按模拟结果选取每种果实的一份推荐。

这些结果是**所述有限候选范围内的最佳推荐**，没有穷举全部 `25` 格排列、全部助手分工和所有动态换阵策略，不能称为全部机制的全局最优证明。自然枯萎掉果与自播、寄生复制、Enigma 原株进化、手动切换 Boost/Rich、阶段性切换光环阵和游荡宝可梦收益，均不属于本次普通种收优化目标。单目标光环的峰值也不等于全田总产量最大。

仿真从辅助株已经成熟的平台开始，生产格从真实扣种播种开始。初次建阵、解锁、购买种子和道具的等待不计入产量。测量窗口按品种自适应为 `0.5～32` 小时，具体时长保存在每条结果的 `measured.hours`。较慢树果需要更长窗口才能完成采收。期末仍在田里的种子已经扣除，未来收成不预先入账。

事件推进沿用 `0.1` 秒游戏边界，只跳过没有阶段、肥料或助手工作事件的时间；在事件所在的最后一帧按格子的实际顺序更新。50ms 光环通知节流被关闭，派生光环按源码同公式缓存，并在植物、阶段或肥料变化时重算。没有复现游戏 `numeric: 5` 的逐 tick 舍入，因此属于源码执行链上的离线数值估算。随机突变与游荡事件关闭；成熟 Babiri 模板用于排除所列原株进化风险，不代表从空田建阵阶段已经免疫一切随机占位。

Petaya 只保护本田其他树果，自身仍会老去。没有 Decay 或 Death 光环时，成熟后的保护期约为 `345600 / 2.75 = 125672.73` 秒，即 `34.91` 小时。保护到期、重新播种、辅助株复建会造成停产，报告中的成熟平台产量不能当作永久全天平均。光环章节的保活窗口方案同样受此限制。

## 文件用途

| 文件 | 用途 |
| --- | --- |
| `generate.cjs` | 读取本地树果与农场源码，生成树果布局候选及数值结果 |
| `coins.cjs` | 农场币候选搜索，分别比较毛币与工资、肥料后的净币 |
| `render-report.cjs` | 将所有结果写入可离线使用的 HTML 与 Markdown |
| `validate.cjs` | 布局导入、职责覆盖、防护、缓存与逐 tick 对照检查 |
| `production-2.75.json` | 70 种树果的最终推荐、其他候选、模拟指标 |
| `coins-data.json` | 农场币搜索范围与推荐 |
| `aura-data.json` | 全部光环的峰值、公式、证明边界和完整布局 |
| `berry-data.json` | 从当前 `BerryList` 提取的树果基础数据 |
| `mechanics-notes.md` | 助手、钱包、原株进化和特殊机制的源码审计 |

## 重算与检查

使用现有项目依赖中的 `typescript`、`knockout`，不需要安装新依赖。脚本默认查找 `E:/myCode/pokeclicker/node_modules`；不同机器可设置 `FARM_ANALYSIS_DEPS`。所有命令从仓库根目录运行。

```bash
FARM_ANALYSIS_DEPS=/path/to/node_modules node design/farm-layout-analysis/generate.cjs
node design/farm-layout-analysis/coins.cjs
node design/farm-layout-analysis/validate.cjs --data design/farm-layout-analysis/production-2.75.json --require-complete
node design/farm-layout-analysis/render-report.cjs
```

`generate.cjs` 支持 `FARM_GROWTH`、`FARM_BERRIES`、`FARM_OUTPUT`、`FARM_RESET`、`FARM_RESTARTS`、`FARM_ITERATIONS`、`FARM_HOURS`。`FARM_BERRIES` 是逗号分隔的树果编号；分批计算时使用不同输出文件，最终按果实编号合并，避免多个进程同时写同一个结果文件。相同果实的候选随机种子独立于分批顺序。

更换源码、倍率或搜索参数后应使用 `FARM_RESET=1` 或新的输出文件，避免沿用旧缓存。光环数据中的静态枚举另有明确公式与验证记录，不能通过更改 `FARM_GROWTH` 将其解释成长期平均。

导入时复制**单个方案的 `plan` 或 `layout` 对象**，不要复制汇总 JSON。布局不包含助手雇用、等级、Allowed Plots、启用状态或物品库存；报告为每条方案另外提供助手负责的行列。游戏中导入后先核对预览，再启用。

## 已完成的复核

- 70 种树果的推荐与备用共 280 份布局均经过真实 `FarmLayoutPlan.parse`，助手负责范围完整覆盖 25 格且互不重叠；52 份特殊树果布局满足四株 Babiri 的全场覆盖。
- Cheri、Wacan、Passho、Lum、Enigma、Petaya 六组短窗口中，光环缓存与源码原始派生的产出、肥料和职责结果一致。
- 四组采收与助手工作边界检查中，事件推进与逐 `0.1` 秒推进的产出、肥料相同；其精度边界仍如前文所述。
- 26 份光环布局经过真实 `Plot` 光环公式重算；全局峰值枚举 245,506 组 Lum 子集，并用乐观上界排除更多 Lum 的情况。
- HTML 中逐方案核对 25 格、完整 JSON 导入及复制，另核对分类、搜索、空结果、剪贴板不可用时的全文选中与离线依赖。
- 实际 Chrome 在 `1440px` 与 `390px` 视口核对排版、长标题、复制按钮和助手行列，无横向溢出。

本次验证针对新生成的文档、数据与离线计算工具。游戏源码没有变更，因此没有把攻略验证冒充游戏全量测试或真实存档运行验收。
