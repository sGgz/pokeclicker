# 自用玩法优化设计：地牢助手寻路与取消道具涨价

> 日期：2026-09-28。状态：设计提案，尚未实现、部署或迁移真实存档。
> 核查基线：本地提交 `08083ee05209424a2542d375e6672fc05ebc7fad`，游戏 `0.10.26`。
> 目标：提高自用体验，同时控制合并官方更新、旧存档导入、网页与桌面同步的维护成本。本文依据当前仓库，不代表未来官方版本的兼容承诺。
> 云存档架构见 [原设计](cloud-save-design.md)；实际交付状态见 [实现记录](cloud-save-implementation.md)。

## 1. 推荐结论

本次范围仅为 **地牢助手寻路逻辑** 和 **去除道具购买涨价**。通过集中模块与少量接入点实现，保留官方存档主体。

- 寻路只改善“下一步走哪里”：正确区分不可达、减少重复搜索、稳定目标选择、减少无意义回头。沿用原助手身份、感知范围、解锁条件和行动间隔。
- 原整批收费、批量折扣、尝试次数、解雇和胜负结算照旧。本次不新增连刷控制器、预算、单局收费、失败即停、接管或任务队列。
- 去除涨价按“固定基础价”设计，同时覆盖报价、Max 和实际扣款。原商品定义与旧倍率保留，固定价期间冻结倍率写入；可切回官方动态价格。
- 两个功能可以分别切回官方模式。无自用配置的旧档默认官方模式，用户在此存档开启后保存选择，不在导入时偷偷改规则。
- 核心实现不需要修改 Worker 协议或增加新的 `App.game` 存档模块。跨设备发布先采用网页和 EXE 同时升级、停用旧端自动同步；自动拦截旧客户端另行评估，不作为这两项功能的实施前提。

“最小影响”指少量集中改动、旧字段可保留、原规则可回退。价格退款旁路仍需处理，但不为此扩展成完整的经济审计或反作弊系统。

## 2. 当前实现：先明确哪些功能已经存在

### 2.1 地牢助手

当前 `DungeonGuides` 已有批量自动进入、自动移动、开箱、下楼和开启 Boss 战，不需要另做一套基本自动刷本。助手没有经验或升级系统；尝试次数和成功次数只是统计。

| 助手 | 行动间隔 | 当前策略 | 解锁进度 |
| --- | ---: | --- | --- |
| Jimmy | 2 秒 | 相邻格加权随机，偏向未走格、宝箱和出口 | 默认助手；地牢本身仍有门槛 |
| Timmy | 2 秒 | 优先寻找路径长度不超过 3 的宝箱，再随机 | 城都 |
| Shelly | 1.5 秒 | 优先近处未探索格，再随机 | 丰缘 |
| Angeline | 1 秒 | 本层宝箱优先，然后探索 | 卡洛斯 |
| Georgia | 0.9 秒 | 寻找 Boss／楼梯，尽量绕开敌人格 | 阿罗拉 |
| Drake | 0.8 秒 | 最短路径去 Boss／楼梯 | 伽勒尔 |

现有批量雇用会一次扣整批费用与门票，助手费带批量折扣；失败也消耗尝试次数。手动 Fire 通常不退预付款，当前任务也不能在刷新后完整恢复。这些是原有行为，本次只改寻路，不调整收费或任务恢复规则。

证据：[助手及费用](../src/scripts/dungeons/DungeonGuides.ts)、[开始／结束地牢](../src/scripts/dungeons/DungeonRunner.ts)、[原界面帮助](../src/components/dungeonGuidesModal.html)、[助手统计](../src/modules/DataStore/StatisticStore/index.ts)。

### 2.2 道具价格

当前普通商店卡片、Max 按钮、是否买得起和扣款都通过 `Item.totalPrice()` 计算。购买成功后调用 `increasePriceMultiplier()`；战斗／农场事件调用 `decreasePriceMultiplier()`。倍率保存在 `player._itemMultipliers`，以商品 `saveName` 为键。

默认倍率是 `1.00045`，但维生素、钥石有 `1.1`，联盟等商店的大师球有 `1.35` 且不设有限上限。因此仅把 `ITEM_PRICE_MULTIPLIER` 改成 1 会漏掉这些商品。

`item.price` 还会在打开商店和倍率变动时刷新。仅修改 multiplier 后，这个内部值仍可能受旧倍率影响。当前卡片走 `totalPrice`，不能据此误报为已经发现卡片与扣款不一致；最小方案保留此官方报价缓存，在 `totalPrice` 集中处理固定报价，并逐一核查退款等旁路。

特别旁路：`refund-vitamins` 一次性兑换码直接读取旧倍率计算退款。固定价买入后按旧高价退回，会改变经济结果，必须单独处理。

证据：[Item](../src/modules/items/Item.ts)、[商店协调](../src/scripts/shop/ShopHandler.ts)、[卡片总价](../src/components/shopModal.html)、[维生素退款](../src/modules/codes/RedeemableCodes.ts)。

## 3. 地牢助手：只修改寻路决策

### 3.1 已核实的代码问题

| 位置 | 当前行为 | 影响与修正方向 |

### 3.2 每位助手怎么改

| 助手 | 优化后的目标选择 | 保留的能力限制 |
| --- | --- | --- |
| Jimmy | 相邻候选优先未探索、减少无意义原路返回；必须回头时允许回头 | 只考虑原相邻格，不全图找 Boss 或宝箱 |
| Timmy | 从路径距离不超过 3 的宝箱中选择最近可达目标；同距时稳定选择 | 找不到时用改良的相邻探索，不扩大嗅探范围 |
| Shelly | 优先 3 步内最近未探索目标，跳过无效目标 | 不增加全图宝箱或 Boss 感知 |
| Angeline | 本层最近可达宝箱优先，随后寻找未探索目标 | 保留宝箱优先定位，不另外加入通关优先模式 |
| Georgia | 优先走能避开敌人的最短路径；不存在时再选普通最短路径 | 保留避敌定位，不提高行动速度 |
| Drake | 稳定选择到本层 Boss／楼梯的最短路径 | 不绕战斗规则，不根据未开宝箱的内容取巧 |

Jimmy 的探索优先级属于明确的寻路策略改善；其他助手的目标种类与感知范围沿用当前定义。减少回头是偏好，不是禁止重复经过格子，否则会把死路变成卡死。

### 3.3 最小实现结构

新增一个 `DungeonGuidePlanner`，输入当前地图、楼层、位置和助手策略，输出 `move(nextTile)`、`interact`、`wait` 或 `no-route`。六位助手的 walk 接入同一个规划器，最终动作仍调用原 `map.moveToTile()`。`interact` / `wait` 只让 walk 停止移动并返回；开箱、楼梯与 Boss 交互仍只由原 tick 执行，不能在规划器调用后额外重复交互。

- 普通助手每次决策最多做一次 BFS；Georgia 先做避敌 BFS，仅避敌不可达时再做普通 BFS。Jimmy 的相邻选择可以直接完成，不必搜索全图。当前地图规模不需要额外寻路框架。
- 同一次决策复用计算结果，首版不做跨 tick 的整条路径缓存，避免宝箱消失、敌人格变化后读取过期路线。
- 只记录当前目标、上一步位置和上次实际移动后的预期位置。以地图实例、楼层、助手和模式作为有效性条件；当前位置与预期不符视为外部移动，丢弃短期目标。目标失效、楼层或地图改变、切换助手或模式时同样丢弃。记录只在内存中，不写入存档或云档。
- 目标就在当前格时输出交互，不去访问空路径的 `path[0]`。下一步必须在同层、边界内且与当前位置相邻；由原访问检查决定能否移动，不能利用已访问格可直达的规则跳过中间路程。
- 无路径时，按该助手原能力选择其他目标或相邻探索；不自动重新雇用、不退出付费局、不改剩余次数。真实异常只给出节流提示并等待原生命周期处理。
- 战斗、捕获等待与已结束地牢不发出移动指令；地图数据暂不可用时安全返回。规划器没有计时器、异步捕获回调或扣费能力。

当前 `findShortestPath()` 在 src 中只有助手调用。为便于保留官方模式及合并更新，首版不改其公共行为；优化模式集中使用新规划器，官方模式仍走原 walk。不要把新算法复制到六份 walk 中。

### 3.4 既有生命周期风险的处理

原地牢有捕获延迟回调，以及结束通知可能重复触发的风险。它们属于原生命周期，本次不顺带重写 `DungeonRunner`、`DungeonBattle`、收费或批量重开流程，也不宣称已消除这些风险。

寻路实现必须做相关回归：战斗／捕获时不移动，结束后不执行过期目标，原收费和尝试统计一致。如果验收发现新寻路引入或放大了生命周期故障，应阻止该功能发布并定位；确需修复原生命周期时，另列明确问题和独立补丁。

## 4. 取消道具涨价：推荐固定基础价模式

### 4.1 行为定义

设商品基础价为 B，购买数量为 N：

这里的“去除涨价”是恢复按基础价购买，不是把旧档当前高价锁死。例如原来已经涨到 16,000 的商品，基础价若为 2,000，开启后就是 2,000。只禁止 `increasePriceMultiplier()` 还不够：现有 `totalPrice()` 会在一次批量购买内逐件递增，必须一并改为线性总价。本次不增加第三种“冻结当前高价”模式。

- `official`：走现有计算和倍率变化逻辑，已有价格与舍入行为保持原样；原 `multiplier === 1` 分支不额外添加舍入。
- `base-price`：在满足原商品可购买条件时，总价为 `round(B × N)`，数量仍受商品上限限制；单价为基础价，不读取历史倍率参与报价。
- 不把道具变成免费，不修改钱包余额、已有数量、稀有度、奖励、解锁条件、货币类型或售罄判断。
- 不可购买的 `Infinity` 基础价仍不可购买；固定价交易拒绝非有限、非正整数、超过安全整数范围的数量，以及非有限总价，不能让 NaN／Infinity 进入钱包或存档。固定价报价接口先处理 `totalPrice(0) = 0`，避免 `Infinity × 0` 变成 NaN，供数量输入和 Max 的二分查找使用；零数量不得触发扣款或发道具。
- 不改变原商品的 multiplier、maxMultiplier、saveName，也不批量清空旧存档 `_itemMultipliers`。
- 基础价模式中，`increasePriceMultiplier()` 和 `decreasePriceMultiplier()` 直接返回，不修改历史倍率与官方报价缓存；显示重算由 `totalPrice()` 对模式的可观察依赖完成。

例如旧存档某商品基础价 2,000、历史倍率 8：开启后每件 2,000，买 100 件花 200,000；历史倍率仍为 8。关闭后回到每件 16,000，并从这个倍率继续原有购买和降价过程。不会补扣之前少付的钱，也不会退还过去多付的钱。

冻结比“隐藏涨价、后台仍然累计”更适合这次改造：大师球原倍率 1.35 且无有限上限，固定低价允许大量购买后，后台继续指数增长可能溢出为 Infinity，JSON 又会把它写成 null。两个倍率写入处增加模式判断，可以避免引入这种新风险。

### 4.2 最小修改范围

新增小模块 `PricingPolicy`，负责读取当前模式、验证数量并决定是否使用固定总价。官方模式分支保留现有公式，不重新实现一份官方公式。最小版本继续把 `item.price` 当作原官方报价缓存，固定模式的界面和交易都使用 `totalPrice()`，不为内部缓存再重构一圈调用方。

| 位置 | 计划修改 |
| --- | --- |
| `Item.totalPrice()` | 基础价模式的早返回；原分支保留。普通商店显示、Max、按钮和扣款继续共用这个入口 |
| `Item.increasePriceMultiplier()` / `decreasePriceMultiplier()` | 基础价模式不写历史倍率；官方模式照旧 |
| `ShopHandler.showShop()` | 最小版本不改，仍维护原官方报价缓存；它不是当前卡片总价和扣款的入口 |
| 模式切换 | `totalPrice()` 使用可观察的模式读取，使界面立即重算；不能使用只读 peek 导致界面不刷新。按货币临时创建的大师球同样走此路径 |
| 自用设置界面 | 一个明确的价格模式选择，说明切回后会恢复旧倍率 |
| 维生素退款处理 | 见下一节，不可遗漏 |

不逐个修改 ItemList、TownList 中的几百条道具配置。维生素、钥石、六种货币的大师球等通过相同入口覆盖；这样新官方商品继承 Item 时通常可自然接入，但每次上游更新仍需检查有没有新的专用购买／退款入口。

MegaStoneItem、BuyOakItem、BuyKeyItem 自己的 `totalPrice()` 已经按固定价处理，本次不重写这些覆盖方法。不能为了统一实现顺带修改原本不涨价的专用商店。

### 4.3 维生素退款码必须处理

现有 `refund-vitamins` 没有逐笔购买记录，而是使用当前倍率估算退款。不能在固定价模式里沿用高倍率退款，也不能靠“切回官方模式”绕过限制。

推荐最小处理：首次成功按固定价买入任意维生素时，将本存档 `ggzz.private.fixedVitaminPurchased` 设为 true；之后在此定制版本中停用旧的维生素退款码，并解释不再具备可靠的历史购入价格。模式切换、刷新、正常云同步不清除该标记。未发生固定价维生素购买的存档保留原退款行为。

标记写在 `Item.buy()` 扣款成功的对应购买路径，不放进 `Vitamin.gain()`，因为兑换和奖励也会调用 gain。用稳定的维生素种类名单识别，避免 Item 反向导入 Vitamin 造成循环依赖。退款检查既要在弹出确认框前执行，也要在异步确认返回后、扣道具／返钱前再次执行，防止确认期间发生固定价购买。

该标记跟随当前完整存档保存，不是反作弊或防修改凭据。官方版／旧版重新保存可能丢弃它，恢复历史备份也会恢复当时的状态，不能承诺任意往返都保留该记录。本次不新增 Worker 强制保留标记、不禁止恢复旧备份，也不跟踪跨槽位的购买历史。

如果不希望增加退款例外，可将第一版固定价范围限定为常规消耗品，暂时排除维生素，再单独实现退款策略。若要求所有商品都固定价，退款处理是必要工作，而非可选的后续修补。首版不为此增加完整购买流水账，也不追溯推算旧存档成本。

### 4.4 比较其他改法

| 方案 | 修改成本 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 只让购买后的倍率不再增加 | 极低 | 一次批量购买内部仍然递增计价；旧档价格也不会恢复基础价 | 不选 |
| 只把全局默认倍率改为 1 | 极低 | 漏掉显式的 1.1／1.35；旧倍率与旁路未处理 | 不选 |
| 把所有道具 multiplier 改为 1 | 表面较低 | 扫大量定义，破坏依赖该倍率的旧退款算法，官方新增商品还得继续改 | 不选 |
| 加载时清空全部旧倍率 | 较低 | 永久改写旧档，回官方时历史价格已丢失 | 不选 |
| 固定报价，后台仍按官方增长倍率 | 较低 | 大师球批量购买可能造成非有限倍率；切回官方突然变得极贵 | 不选 |
| 固定基础价、冻结旧倍率、保留原模式 | 小范围集中修改 | 要处理退款和跨版本设置 | 推荐 |

这里仅覆盖继承普通 Item 购买机制的商品。树果大师兑换、宝石／碎片兑换、挖矿商店、升级系统、地牢助手费等有各自规则，不因为打开固定道具价格就全部变成固定价。若要修改这些，必须逐个列为额外范围。

## 5. 自用配置如何保存

首版复用原 `settings`，注册带前缀的独立配置，示意如下：

```json
{
  "ggzz.private.pricingMode": "official",
  "ggzz.private.fixedVitaminPurchased": false,
  "ggzz.private.guidePathfinding": "official"
}
```

- 新配置设为 **不保存为全局默认值**，防止某个训练家启用后影响其他槽位。每次载入／导入前先初始化本槽位自用默认值，再应用当前配置。
- 价格模式限定 `official` / `base-price`，寻路模式限定 `official` / `optimized`。两个开关分别选择，允许单独对照官方行为。
- 布尔值严格校验，不直接依赖 `BooleanSetting` 的 `!!value` 处理外部 JSON，因为字符串 `"false"` 会被当作 true。无效模式回到官方模式并提示；退款历史值若明确损坏，应提示并暂拒绝该退款，不能当成确认没有低价购买。
- 三个独立设置不需要通用配置容器、新存档 schema 或独立迁移框架；将来确实发生格式变化时再设计对应迁移。
- 不保存当前目标、路径、地图、坐标、运行中的批次或钱包副本。地图／位置变化后从实际状态重新规划。

配置由现有 `Save.store()`、官方格式 `.txt` 和云存档 payload 的 settings 部分共同保存；不修改 `save.update.version` 或云 envelope 的 schemaVersion。

## 6. 必须区分的兼容性

| 场景 | 设计目标与边界 |
| --- | --- |
| 当前官方格式旧档 → 新定制版 | player/save 原字段不迁移；自用设置缺省走官方模式；开启功能前导出备份 |
| 新定制网页 ↔ 新定制 EXE | 使用同一份功能实现；配置随完整快照同步，路径和当前目标不跟过去 |
| 新定制版 → 同游戏版本官方版 | 核心字段尽量保持可读取；官方端不理解增强开关、可能丢弃它们；必须用副本实测后才称兼容 |
| 在官方版保存后再回定制版 | 自用设置和标记可能已丢失；不能承诺完整往返。缺少上下文不得自动重新开启增强功能 |
| 新官方游戏版本 → 旧定制 EXE | 仍应被原游戏版本检查拒绝；更新定制代码并打包后再使用 |
| 新定制版 → 老定制客户端 | 核心结构保持原格式，但旧端可能丢掉三个新设置；本次不会自动拦截这种同版本上传 |

`Settings.fromJSON()` 会忽略未注册的设置；`Settings.toJSON()` 只输出已注册的设置。因此“官方会忽略未知字段”不等于“官方会原样保留未知字段”。单独把数据塞进 player／save 任意位置同样不能保证被原序列化保留。

固定价买入的商品、少花的钱、助手刷到的奖励都是真实进度。关闭功能只恢复规则，不能恢复经济历史。要求回到改造前状态，只能恢复改造前完整备份，且会失去备份后的进度。核验兼容时使用隔离槽位和备份副本，不覆盖正在使用的云档，也不得调低版本号绕过原检查。

## 7. 网页和桌面的发布配套

当前云端只按 `gameVersion` 拒绝降级，`clientBuild` 只是记录；两个同为 0.10.26 的客户端可能一个认识自用字段，另一个完全不认识，后者仍可能覆盖前者。

本次采用人工统一版本的发布流程，不修改 Worker：

1. 从当前实际使用的客户端导出完整备份，暂停各旧端自动同步。
2. 用同一份提交构建网页和 Windows EXE，记录游戏版本、定制提交和桌面版本。
3. 更新网页，关闭旧网页标签并重新加载；安装／打开新版 EXE，关闭旧 EXE。另一台电脑也完成更新后再同步。
4. 在副本上启用两个开关，验证网页 → EXE → 网页往返后价格模式、退款标记和进度一致。
5. 确认所有使用中的端已升级，再恢复自动同步。原官方客户端只用于副本核验，不当作保留自用设置的同步中转。

这个流程依赖用户停用旧端，不能声称后台已经具备强制保护。若以后希望“忘记更新的旧 EXE 也绝对不能覆盖新配置”，再独立增加最低客户端代次检查，保留已成功请求重放并验证冲突处理。该项属于后续同步增强，不在本次两项玩法改动内。

## 8. 代码组织与官方更新合并

建议新增目录 `src/modules/privateGameplay/`，只放实际需要的模块：

```text
settings.ts                  三个自用设置及严格校验
PricingPolicy.ts             有效报价与价格模式
DungeonGuidePlanner.ts       六名助手的下一步决策
index.ts                     小范围导出与初始化
```

这不是另起一个插件系统。两个模式确实存在差异，才需要这些接入点。规划尽量返回结果，由现有逻辑执行；测试与正式调用使用相同接口。

| 现有文件 | 预期接入责任 |
| --- | --- |
| `src/modules/settings/index.ts` | 注册自用设置，避免修改大量原设置定义 |
| `Item.ts` | 总价模式分支、倍率冻结、固定价维生素购买标记；现有 ShopHandler 最小版本不改 |
| `RedeemableCodes.ts` | 对有固定价维生素历史的档阻止旧退款算法 |
| `DungeonGuides.ts` | 六个 walk 的模式选择与规划器调用；保留原列表顺序和生命周期 |
| 新旧模块桥接文件 | 对旧全局脚本暴露少量接口，不挂任意新全局状态 |
| `settingsModal.html` | 价格、寻路两个开关及行为说明；退款标记隐藏 |

`DungeonMap.ts`、`DungeonRunner.ts`、`DungeonBattle.ts`、`Game.ts`、`Save.ts`、`Player.ts`、`ShopHandler.ts` 和 Worker 不是本次预期修改点。若实施中发现必须改这些文件，应先说明具体依赖并优先寻找更小接入面，而不是预先将整个生命周期纳入重构。

官方更新流程：

1. 保存当前可玩的安装包、网页发布版本和完整存档备份；工作区保持干净。
2. 记录已合并的官方 SHA。新建绑定分支的测试 worktree，在自用分支上合并官方明确的 tag/SHA；共享分支优先 merge，不改写已分享历史。
3. 人工复查官方是否改变 Item 购买路径、退款入口、地牢结算、助手索引、设置序列化和存档迁移。无文本冲突也不能视为兼容验证成功。
4. 跑下述定向回归与已有项目检查；从复制的旧档做真实加载测试，禁止拿唯一真实存档当测试夹具。
5. 两端验收通过后再部署、打包和升级。发布过程不覆盖 `.env`、Worker Secret、用户本机数据或 GitHub 存档仓库。

不维护第二套 `Update.ts` 上游迁移表。未来官方实现同类功能时，明确转用官方能力并删除重复实现，保留必要的设置兼容处理。

## 9. 实施前应具备的验收用例

### 价格

- 开关关闭时，新旧档价格、单买、批量、封顶和 Max 与当前代码一致。
- 已有 8 倍／100 倍价格的档，开启后报价和扣款都是基础价；倍率 JSON 不被清零。
- 普通道具、普通精灵球、维生素、钥石、六币种大师球均覆盖；不动非 Item 兑换商店。
- 固定模式购买与战斗后旧倍率保持不变；切回官方模式按旧倍率继续。
- 固定价大量买大师球不写出 Infinity／NaN；实际扣款为有限值，单次购买数量为安全整数，报价与发放数量一致。
- 商店打开期间切换模式、重新打开商店、切换临时商品实例均刷新正确。
- 固定价买维生素后退款码被阻止；切模式、刷新及同一新版快照的云往返保留标记。恢复历史备份或经过旧端后不承诺保留，见兼容边界。
- 维生素兑换、奖励、失败购买不误设标记；退款确认框等待期间发生固定价购买，确认后也不能扣道具或返钱。

### 地牢寻路

- 目标同格、目标相邻、没有候选、边界格、非法目标均有明确结果，不访问 `undefined`。
- Georgia 避敌不可达时才回退普通路径；合法的一步避敌路径不被误判；Drake 保持普通最少步数。
- 多个同距宝箱时选择稳定；Jimmy 减少无意义回头但仍能退出死路；Timmy／Shelly 不超过原 3 步感知范围。
- 所有移动只走当前层相邻一步；处于交互目标时先交还原交互流程；战斗／捕获时等待。
- 换楼层、换地图、玩家改变位置、切换助手或模式后不沿用过期目标。刷新和云恢复不会恢复路径记忆。
- 同一地图样本对照实际走步数、搜索次数、重复走格和超时率；不预先承诺百分比收益，也不要求所有助手都像 Drake。
- 雇用费用、批量折扣、行动间隔、尝试次数与助手统计保持原规则；原列表索引不变。
- 多层、多局，以及 Boss／训练师捕获接近超时做集成回归。新寻路引入的错误必须修复；原生命周期缺陷单列，不混成寻路改造已经解决。

### 存档和发布

- 当前官方基线 `.txt` 导入新定制端默认官方模式；备份可读。
- 新定制网页 → 新 EXE → 新网页，三个设置和进度一致；路径和目标不写入存档。
- 更高 gameVersion 继续由原检查保护；未知或损坏的自用设置按严格校验处理，不误开功能。
- 复制的存档在同版官方代码加载、保存、导出、再导入，实测核心字段与自用字段各自的保留／丢失，不用“未报错”代替核对。
- 原存档字段、助手统计数组、商品倍率表、官方游戏版本号没有被重排、清空或改写。
- 运行现有 `cloud:check`、`cloud:build`、`desktop:test`，再用一键脚本生成新 EXE 并做隔离存档运行验收。设计文档本身不需要重新打包游戏。

## 10. 建议实施顺序

| 批次 | 内容 | 交付后可观察结果 |
| --- | --- | --- |
| A | 寻路规划器、六位助手接入、官方／优化模式 | 路径结果明确、同源搜索复用、减少无意义绕路；原收费和批量流程保留 |
| B | 固定基础价、倍率冻结、退款保护、相关设置 | 单买与批量都按基础价；旧倍率保留，可切回官方规则 |
| 发布配套 | 同提交网页和 EXE、备份、停用旧端、往返验收 | 新版之间设置与进度一致；明确旧端仍可能丢设置，不宣称自动拦截 |

每批单独提交、单独验收；正式发布前准备新版网页和 EXE。方案采用集中接入和保留旧字段降低维护成本，但官方未来若重构地牢或道具系统，仍需要人工适配，不能承诺以后更新永远零冲突。
