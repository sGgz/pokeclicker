# 自用玩法优化设计：地牢助手与固定道具价格

> 日期：2026-09-28。状态：设计提案，尚未实现、部署或迁移真实存档。
> 核查基线：本地提交 `08083ee05209424a2542d375e6672fc05ebc7fad`，游戏 `0.10.26`。
> 目标：提高自用体验，同时控制合并官方更新、旧存档导入、网页与桌面同步的维护成本。本文依据当前仓库，不代表未来官方版本的兼容承诺。
> 云存档架构见 [原设计](cloud-save-design.md)；实际交付状态见 [实现记录](cloud-save-implementation.md)。

## 1. 推荐结论

采用两个独立、可关闭的功能：**地牢助手增强**和**道具按基础价购买**。集中放在自用模块，通过少量明确的调用点接入原代码；不复制整套地牢、钱包或存档系统，也不通过运行时替换原函数实现。

- 地牢第一阶段做“有限次数连刷、每局付费、失败即停、预算限制、本局结束后停止、运行摘要”。第二阶段再改善寻路。复用原助手身份、解锁条件、行动间隔、战斗、捕获、奖励和统计。
- 固定价格使用 `official` / `base-price` 两种模式。基础价模式同时影响报价、Max 数量和实际扣款；原道具定义与旧存档倍率保留，开启期间冻结涨价和降价倍率写入。
- 新存档和无配置的旧档默认官方模式；用户在此存档中开启一次后随存档保存。开启固定价时，已有的高倍率不会继续影响当前报价；切回官方模式恢复原倍率，不退款、不重算历史经济。
- 不新增助手经验、装备、技能点、自动任务队列或跨设备执行状态，首版不增加新的 `App.game` 存档模块。
- 同一份云档正式用于网页和 EXE 前，两端要具备同一代自用功能，并增加 Worker 的旧客户端写入保护。只有 `gameVersion` 相同不足以证明兼容。

这里的“最小影响”指修改位置少、保留官方数据结构且容易验证，不是只追求少改一行。价格旁路和旧客户端覆盖问题不能省略。

## 2. 当前实现：先明确哪些功能已经存在

### 2.1 地牢助手

当前 `DungeonGuides` 已有批量自动进入、自动移动、开箱、下楼和开启 Boss 战，不需要另做一套基本自动刷本。助手没有经验或升级系统；尝试次数和成功次数只是统计。

| 助手 | 行动间隔 | 当前策略 | 解锁进度 |
| --- | ---: | --- | --- |
| Jimmy | 2 秒 | 相邻格加权随机，偏向未走格、宝箱和出口 | 默认助手；地牢本身仍有门槛 |
| Timmy | 2 秒 | 优先寻找路径长度不超过 3 的宝箱，再随机 | 城都 |
| Shelly | 1.5 秒 | 优先近处未探索格，再随机 | 丰缘 |
| Angeline | 1 秒 | 本层宝箱优先，然后探索 | 卡洛斯 |
| Georgia | 0.9 秒 | 寻找 Boss／楼梯，尽量绕开敌人格 | 阿罗拉 |
| Drake | 0.8 秒 | 最短路径去 Boss／楼梯 | 伽勒尔 |

现有费用和批量行为：

1. 雇用时一次性扣整批助手费用与门票。助手费用有批量折扣，使用 `次数 ^ 0.975`，门票没有该折扣。
2. 每次进本扣一次“剩余尝试次数”；失败也消耗次数。界面里的 Attempts 不能解释为保证成功次数。
3. 胜利、失败或离开流程会通知助手，剩余次数大于零则尝试再进本。
4. 手动 `Fire` 不退剩余预付款。因地牢不能继续进入而停止时有一条比例退款路径，不能把这个例外宣传为“随时退款”。
5. 助手的雇用状态、剩余预付次数、当前地图并不作为可恢复模块存档；费用和完成统计会保存。因此预付很多次后刷新不能保证把剩余局恢复回来。

证据：[助手及费用](../src/scripts/dungeons/DungeonGuides.ts)、[开始／结束地牢](../src/scripts/dungeons/DungeonRunner.ts)、[原界面帮助](../src/components/dungeonGuidesModal.html)、[助手统计](../src/modules/DataStore/StatisticStore/index.ts)。

### 2.2 道具价格

当前普通商店卡片、Max 按钮、是否买得起和扣款都通过 `Item.totalPrice()` 计算。购买成功后调用 `increasePriceMultiplier()`；战斗／农场事件调用 `decreasePriceMultiplier()`。倍率保存在 `player._itemMultipliers`，以商品 `saveName` 为键。

默认倍率是 `1.00045`，但维生素、钥石有 `1.1`，联盟等商店的大师球有 `1.35` 且不设有限上限。因此仅把 `ITEM_PRICE_MULTIPLIER` 改成 1 会漏掉这些商品。

`item.price` 还会在打开商店和倍率变动时刷新。仅修改 multiplier 后，这个内部值仍可能受旧倍率影响。当前卡片走 `totalPrice`，不能据此误报为已经发现卡片与扣款不一致；最小方案保留此官方报价缓存，在 `totalPrice` 集中处理固定报价，并逐一核查退款等旁路。

特别旁路：`refund-vitamins` 一次性兑换码直接读取旧倍率计算退款。固定价买入后按旧高价退回，会改变经济结果，必须单独处理。

证据：[Item](../src/modules/items/Item.ts)、[商店协调](../src/scripts/shop/ShopHandler.ts)、[卡片总价](../src/components/shopModal.html)、[维生素退款](../src/modules/codes/RedeemableCodes.ts)。

## 3. 地牢助手第一阶段：先把连刷做得可控

### 3.1 两种收费方式分开

保留原“整批预付”功能。新增独立入口“自用连刷”，每次调用原雇用流程购买 **1 次尝试**，本局结束且符合继续条件时，再启动下一局。

这样不用引入“预付余额如何存档、崩溃后如何退款、官方端不认识余额怎么办”的新问题，也不会发生停止后还丢失几十局预付款。

代价必须在界面写清楚：**自用连刷按单局价格收费，不享受原整批助手费用折扣；当前已经开始的一局不因停止或刷新而退款。** 如果未来确实需要批量折扣，另行设计预付交易记录和中断补偿，不混进首版。

不得直接绕过 `DungeonGuides.hire()` 调用 `initializeDungeon()`：`DungeonRunner` 看到已雇用助手时会认为门票已预付而不再扣票，直接设置 hired 状态容易产生漏扣或重复扣款。

### 3.2 操作与默认值

| 操作／配置 | 推荐行为 |
| --- | --- |
| 选择助手 | 仅可选当前已解锁助手；保留原助手索引 |
| 选择地牢 | 固定为启动时所在的地牢，不跟随用户后来切换的城镇 |
| 尝试次数 | 默认 10 次，正整数，首版范围 1–1,000；界面明确是“尝试” |
| 失败处理 | 默认本局失败后停止，显示原因；未来可增加连续失败上限 |
| 花费上限 | 启动前列出所有涉及货币的单局／最大总费用；可分别设置本次预算或最低保留额 |
| 本局结束后停止 | 当前局照常结算，不开始下一局；是推荐停止按钮 |
| 手动 Fire／退出 | 保留原操作，同时使自用会话失效；当前已付费用按原规则处理，不自动重雇 |
| 立即接管／局内暂停恢复 | 暂不纳入首版；涉及捕获中断、计时和助手通关统计，需独立明确规则后再做 |
| 完成摘要 | 本次尝试数、成功数、失败数、实际各币种花费、停止原因；首版只保留本次会话摘要 |

每次进本前重新检查地牢、助手资格、该地牢已通关 10 次的原界面门槛、钱包和预算，不假设启动时检查一次就永久有效。原静态 hire 并未完整复核这些界面条件，增强入口不能省略。预算按本次成功扣款的报价递增，不用钱包前后差额计算，因为战斗和宝箱同时可能带来收入；一次开始只能扣一次钱。失败时不能为了凑够成功次数无限续跑。

### 3.3 状态与接入位置

新增 `DungeonGuideSession` 管理 `idle → waiting → running → stopping → finished`。所有状态只在当前进程内；配置持久化，执行进度不持久化。

- 原助手仍执行一局的移动与交互；自用会话只负责是否开下一局。不能让原“剩余批次数”与新会话同时管理多局。
- 从原胜利／失败／离开路径传入明确的结果和一次性的 attemptId。原代码可能重复通知结束，新会话必须按 attemptId 只结算、排队一次。
- `DungeonGuides.endDungeon()` 先完成当前原助手的收尾，再发出自用会话的完成通知。下一局安排在之后的正常游戏 tick，避免在结算栈里递归开本。
- 开下一局前核对 sessionId、存档槽位、地牢标识、未人工停止、游戏未关闭／切设备、没有别的控制者。使用游戏循环推进，不能靠独立定时器在 `Game.stop()` 后继续花钱。
- 手动 Fire、退出、换城镇、切槽位、导入／恢复、切设备和关闭游戏都使会话失效。刷新后始终是 idle，不从设置或云档中的次数推断“应该继续”。

另有两处必须一起处理，不能只给新控制器加防重：

- 当前 Boss／训练师捕获有异步回调，可能在本局超时后才返回。`DungeonBattle` 回调必须绑定本局生成编号、存档身份和本次捕获上下文，包括对象、球种及捕获概率；原 `Battle.attemptCatch()` 等方法还读取静态概率和球种，只绑定敌人对象不够。正常连刷应等待本局已发起捕获结算完，再开放下一局；等待期间不得通过另一个入口启动新地牢改写上下文。
- 地牢计时与胜负继续按原规则判定一次：超时时已标记 `defeatedBoss` 的局按原逻辑判胜，其他情况按原逻辑判负。晚到捕获最多结算一次，不能推翻已确定的胜负、推进已结束的地图、给新局增加统计或再次发通关奖励。刷新、主动退出、换档或恢复时必须使旧会话失效；不得把旧档捕获结算到新档，也不因取消回调额外补发奖励或退款。此处属于待实施并验收的异步隔离设计，当前代码尚不具备这些保证。
- 正常结束本来就会自动回城。停止判断要区分“本会话结算返回城镇”和“玩家主动换图”，不能给所有 `moveToTown()` 一律挂停止逻辑。也不能监听 `hired=null` 就重雇，否则用户点 Fire 会被当成继续信号。

模式与按钮需要是明示选择。打开游戏、打开地牢面板、恢复云档都不自动开始任务。

## 4. 地牢助手第二阶段：优化路径，但保留玩法规则

优先优化来回绕路和无效重复搜索，不先提高全局 tick 速度或直接发奖励。

| 优化 | 设计 | 限制 |
| --- | --- | --- |
| 更稳定的探索 | 优先可到达的未探索前沿，记录短期往返位置；同等路径稳定选择 | Jimmy 不因增强模式直接获得全图 Boss 信息 |
| 寻路复用 | 每次决策计算一次距离／前驱，复用给多个候选目标 | 地图、楼层、目标和可走状态变化时失效；不能跨局复用坐标 |
| 防止卡住 | 检查路径是否到达目标、下一步是否有效、实际移动是否成功；连续异常达到阈值则停止并说明 | 正在战斗、捕获等待不算卡死；不可每次异常直接重开付费局 |
| 宝箱与通关取舍 | 对具备相应感知能力的助手，提供宝箱优先／原策略等选项；剩余时间不足时停止额外绕路 | 只选择该助手原本可感知的格子；不得读取未开宝箱的物品 metadata 决定去哪里 |
| 移动速度 | 首版沿用各助手 800–2,000 ms 间隔 | 不跳过战斗／捕获，不直接改玩家坐标绕过原访问检查 |
| 明确反馈 | 显示当前目标、为何等待、最后一次失败原因；通知可在会话结束时汇总 | 不在正常游玩界面暴露调试日志和内部堆栈 |

规划模块只输出下一步目标，由原 `map.moveToTile()` 和 `handleInteraction()` 执行动作。奖励、首通、任务、捕获和统计仍走原函数。不要新增助手到 `DungeonGuides.list` 中间或重排列表，已有尝试／成功统计按数组索引保存。

原 `findShortestPath()` 应做“不可达返回值、空路径、同格目标”回归验证后再复用，不能只凭返回数组非空就相信第一步有效。第一阶段无需重写全局 DungeonMap。

可后续独立评估的自用选项：立即接管、局内暂停恢复、降低助手费、放宽解锁、加快走路。接管需明确助手通关统计归属；暂停不能默认冻结地牢计时。其余玩法平衡改动应各自开关并记录版本，不与稳定性修复绑在一起；助手升级、装备和长期任务队列暂不做。

## 5. 取消道具涨价：推荐固定基础价模式

### 5.1 行为定义

设商品基础价为 B，购买数量为 N：

- `official`：走现有计算和倍率变化逻辑，已有价格与舍入行为保持原样。
- `base-price`：在满足原商品可购买条件时，总价为 `round(B × N)`，数量仍受商品上限限制；单价为基础价，不读取历史倍率参与报价。
- 不把道具变成免费，不修改钱包余额、已有数量、稀有度、奖励、解锁条件、货币类型或售罄判断。
- 不可购买的 `Infinity` 基础价仍不可购买；实际交易拒绝非有限、非正整数、超过安全整数范围的数量，以及非有限总价，不能让 NaN／Infinity 进入钱包或存档。报价接口仍允许 `totalPrice(0) = 0`，供数量输入和 Max 的二分查找使用；零数量不得触发扣款或发道具。
- 不改变原商品的 multiplier、maxMultiplier、saveName，也不批量清空旧存档 `_itemMultipliers`。
- 基础价模式中，`increasePriceMultiplier()` 和 `decreasePriceMultiplier()` 直接返回，不修改历史倍率与官方报价缓存；显示重算由 `totalPrice()` 对模式的可观察依赖完成。

例如旧存档某商品基础价 2,000、历史倍率 8：开启后每件 2,000，买 100 件花 200,000；历史倍率仍为 8。关闭后回到每件 16,000，并从这个倍率继续原有购买和降价过程。不会补扣之前少付的钱，也不会退还过去多付的钱。

冻结比“隐藏涨价、后台仍然累计”更适合这次改造：大师球原倍率 1.35 且无有限上限，固定低价允许大量购买后，后台继续指数增长可能溢出为 Infinity，JSON 又会把它写成 null。两个倍率写入处增加模式判断，可以避免引入这种新风险。

### 5.2 最小修改范围

新增小模块 `PricingPolicy`，负责读取当前模式、验证数量并决定是否使用固定总价。官方模式分支保留现有公式，不重新实现一份官方公式。最小版本继续把 `item.price` 当作原官方报价缓存，固定模式的界面和交易都使用 `totalPrice()`，不为内部缓存再重构一圈调用方。

| 位置 | 计划修改 |
| --- | --- |
| `Item.totalPrice()` | 基础价模式的早返回；原分支保留。普通商店显示、Max、按钮和扣款继续共用这个入口 |
| `Item.increasePriceMultiplier()` / `decreasePriceMultiplier()` | 基础价模式不写历史倍率；官方模式照旧 |
| `ShopHandler.showShop()` | 最小版本不改，仍维护原官方报价缓存；它不是当前卡片总价和扣款的入口 |
| 模式切换 | `totalPrice()` 使用可观察的模式读取，使界面立即重算；不能使用只读 peek 导致界面不刷新。按货币临时创建的大师球同样走此路径 |
| 自用设置界面 | 一个明确的价格模式选择，说明切回后会恢复旧倍率 |
| 维生素退款处理 | 见下一节，不可遗漏 |

不逐个修改 ItemList、TownList 中的几百条道具配置。维生素、钥石、六种货币的大师球等通过相同入口覆盖；这样新官方商品继承 Item 时通常可自然接入，但每次上游更新仍需检查有没有新的专用购买／退款入口。

### 5.3 维生素退款码必须处理

现有 `refund-vitamins` 没有逐笔购买记录，而是使用当前倍率估算退款。不能在固定价模式里沿用高倍率退款，也不能靠“切回官方模式”绕过限制。

推荐最小处理：首次成功按固定价买入任意维生素时，将本存档 `ggzz.private.fixedVitaminPurchased` 设为 true；之后在此定制版本中停用旧的维生素退款码，并解释不再具备可靠的历史购入价格。模式切换、刷新、正常云同步不清除该标记。未发生固定价维生素购买的存档保留原退款行为。

标记写在 `Item.buy()` 扣款成功的对应购买路径，不放进 `Vitamin.gain()`，因为兑换和奖励也会调用 gain。用稳定的维生素种类名单识别，避免 Item 反向导入 Vitamin 造成循环依赖。退款检查既要在弹出确认框前执行，也要在异步确认返回后、扣道具／返钱前再次执行，防止确认期间发生固定价购买。

该标记不是反作弊或防修改凭据。官方版／旧版重新保存可能丢弃它，单靠标记无法保证任意外部存档往返后的经济约束。受保护云槽位已有 true 时，新版客户端恢复旧快照或导入文件也应保守保留 true，Worker 拒绝无说明的清除；恢复至新隔离槽位的旧档是另一份历史，不承诺跨槽位追踪。

如果不希望增加退款例外，可将第一版固定价范围限定为常规消耗品，暂时排除维生素，再单独实现退款策略。若要求所有商品都固定价，退款处理是必要工作，而非可选的后续修补。首版不为此增加完整购买流水账，也不追溯推算旧存档成本。

### 5.4 比较其他改法

| 方案 | 修改成本 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 只把全局默认倍率改为 1 | 极低 | 漏掉显式的 1.1／1.35；旧倍率与旁路未处理 | 不选 |
| 把所有道具 multiplier 改为 1 | 表面较低 | 扫大量定义，破坏依赖该倍率的旧退款算法，官方新增商品还得继续改 | 不选 |
| 加载时清空全部旧倍率 | 较低 | 永久改写旧档，回官方时历史价格已丢失 | 不选 |
| 固定报价，后台仍按官方增长倍率 | 较低 | 大师球批量购买可能造成非有限倍率；切回官方突然变得极贵 | 不选 |
| 固定基础价、冻结旧倍率、保留原模式 | 小范围集中修改 | 要处理退款和跨版本设置 | 推荐 |

这里仅覆盖继承普通 Item 购买机制的商品。树果大师兑换、宝石／碎片兑换、挖矿商店、升级系统、地牢助手费等有各自规则，不因为打开固定道具价格就全部变成固定价。若要修改这些，必须逐个列为额外范围。

## 6. 自用配置如何保存

首版复用原 `settings`，注册带前缀的独立配置，示意如下：

```json
{
  "ggzz.private.schema": 1,
  "ggzz.private.pricingMode": "official",
  "ggzz.private.fixedVitaminPurchased": false,
  "ggzz.private.guideEnhanced": false,
  "ggzz.private.guideAttemptLimit": 10,
  "ggzz.private.guideStopOnLoss": true
}
```

- 新配置设为 **不保存为全局默认值**，防止某个训练家启用后影响其他槽位。每次载入／导入前先初始化本槽位自用默认值，再应用当前配置。
- 模式使用受限字符串；次数必须是有界安全整数；布尔值严格校验。不要直接依赖 `BooleanSetting` 的 `!!value` 来验证外部 JSON，因为字符串 `"false"` 会被当作 true。
- 自用配置有独立迁移函数：缺省视为旧 schema；已知旧 schema 做幂等迁移；配置值错误使用安全默认值并提示。未知的更高 schema 在启动／覆盖前拒绝，保留原始数据，不能静默降级后保存。
- 不在设置内保存定时器、执行中标志、已付剩余次数、地图、坐标、未发放奖励、当前 attemptId 或钱包副本。
- 更详细的预算、策略等后续参数仍独立注册、约束大小。首版不为几个开关引入一个能装任意对象的通用设置容器。

配置由现有 `Save.store()`、官方格式 `.txt` 和云存档 payload 的 settings 部分共同保存；自用 schema 不占用 `save.update.version`，也不必改变云 envelope 的 schemaVersion。

## 7. 必须区分的兼容性

| 场景 | 设计目标与边界 |
| --- | --- |
| 当前官方格式旧档 → 新定制版 | player/save 原字段不迁移；自用设置缺省走官方模式；开启功能前导出备份 |
| 新定制网页 ↔ 新定制 EXE | 同一代自用 schema 和实现；配置随完整快照同步，运行中的连刷不跟过去 |
| 新定制版 → 同游戏版本官方版 | 核心字段尽量保持可读取；官方端不理解增强开关、可能丢弃它们；必须用副本实测后才称兼容 |
| 在官方版保存后再回定制版 | 自用设置和标记可能已丢失；不能承诺完整往返。缺少上下文不得自动重新开启增强功能 |
| 新官方游戏版本 → 旧定制 EXE | 仍应被原游戏版本检查拒绝；更新定制代码并打包后再使用 |
| 新自用 schema → 老定制客户端 | 同 gameVersion 也不能任意覆盖；需要以下客户端代次检查 |

`Settings.fromJSON()` 会忽略未注册的设置；`Settings.toJSON()` 只输出已注册的设置。因此“官方会忽略未知字段”不等于“官方会原样保留未知字段”。单独把数据塞进 player／save 任意位置同样不能保证被原序列化保留。

固定价买入的商品、少花的钱、自动刷到的奖励都是真实进度。关闭功能只恢复规则，不能恢复经济历史。要求回到改造前经济状态，只能恢复改造前完整备份，且会失去备份后的进度；同一受保护云槽位的退款限制标记仍保守保留。若要单独验证改造前状态，使用隔离槽位和备份副本，不覆盖正在使用的云档。不得悄悄把版本号调小以绕过版本检查。

## 8. 网页／桌面／Worker 的版本协调

当前云端只按 `gameVersion` 拒绝降级，`clientBuild` 只是记录；两个同为 0.10.26 的客户端可能一个认识自用字段，另一个完全不认识，后者仍可能覆盖前者。

推荐为定制发布增加 **private client epoch**，与桌面壳版本、官方游戏版本分开。沿用上传中已有 `clientBuild` 字段编码，例如 `0.10.26-cloud-save-2-private-1`，由双方约定严格解析，不能用模糊字符串排序。

自用配置或序列化发生不向后兼容的变更时，必须提高 private epoch，并相应提高受保护部署的 Worker 最低代次；不能只改 schema 而继续让不认识该格式的旧端上传。纯界面调整等兼容变更不必每次提高代次。

正式共用云槽位时：

1. Worker 增加最低自用客户端代次配置。启用后旧客户端 PUT 明确返回 `CLIENT_UPGRADE_REQUIRED`；保留登录、读取／备份能力，不自动将失败写入换成另一个槽位。
2. 新端上传携带正确代次及自用 schema；Worker 同时检查配置格式、受保护标记不能悄悄消失／从 true 变 false。跨代次门槛是兼容保护，不是认证，不替代密码、Origin、SHA 或冲突检查。
3. 无副作用的已成功请求重放仍可以返回原回执；任何新写入必须先满足代次要求。不得因此破坏原丢回执重试与幂等行为。
4. 客户端在启动、恢复、导入和上传前检查自用 schema，不能先运行一轮再发现版本不认识。未写回前保存原始恢复副本。
5. `save.update.version` 仍为上游游戏版本；桌面 `1.x` 版本与 private epoch 分别管理。发布记录保存官方基线、定制提交、游戏版本、桌面版本、private epoch 和验收结果。

上线顺序建议：备份并暂停旧端自动同步 → 准备新版 Worker 和网页 → 安装并核对新版 EXE → 开启最低代次保护 → 开启自用功能 → 完成网页/桌面往返验收。启用保护后，未更新的另一台电脑可以先导出本地档，升级后再同步。

只在本机试用新 EXE 可先做离线副本验收；正式让价格开关跟云档跨设备同步时，不能继续假设旧网页和旧 Worker 自动兼容。最低代次配置需纳入现有配置向导的保留逻辑，重跑向导不得无意解除保护。

## 9. 代码组织与官方更新合并

建议新增目录 `src/modules/privateGameplay/`，只放实际需要的模块：

```text
settings.ts                  自用设置注册、严格校验、独立迁移
PricingPolicy.ts             有效报价与价格模式
DungeonGuideSession.ts       本次有限连刷和停止条件
DungeonGuidePlanner.ts       第二阶段的下一步决策
index.ts                     小范围导出与初始化
```

这不是另起一个插件系统。两个模式确实存在差异，才需要这些接入点。规划尽量返回结果，由现有逻辑执行；测试与正式调用使用相同接口。

| 现有文件 | 预期接入责任 |
| --- | --- |
| `src/modules/settings/index.ts` | 注册自用设置，避免修改大量原设置定义 |
| `Item.ts` | 总价模式分支、倍率冻结、固定价维生素购买标记；现有 ShopHandler 最小版本不改 |
| `RedeemableCodes.ts` | 对有固定价维生素历史的档阻止旧退款算法 |
| `DungeonGuides.ts` | 一局生命周期通知、可选规划器；保留原列表顺序 |
| `DungeonRunner.ts` | 提供明确胜负／离开结果、保证结束通知不会导致重复续局 |
| `DungeonBattle.ts` | 捕获等异步回调按本局编号和对象处理，避免旧局回调影响新局 |
| `Game.ts`、云存档关闭／切换入口 | 必要的会话失效和正常 tick 推进；不建立第二个独立游戏时钟 |
| 新旧模块桥接文件 | 对旧全局脚本暴露少量接口，不挂任意新全局状态 |
| `settingsModal.html`、地牢助手组件 | 自用开关、有限连刷入口与摘要；优先单独组件引入 |
| `CloudSave.ts`、Worker 上传校验和配置 | 自用代次、未知 schema 与旧端覆盖保护 |

官方更新流程：

1. 保存当前可玩的安装包、网页发布版本和完整存档备份；工作区保持干净。
2. 记录已合并的官方 SHA。新建绑定分支的测试 worktree，在自用分支上合并官方明确的 tag/SHA；共享分支优先 merge，不改写已分享历史。
3. 人工复查官方是否改变 Item 购买路径、退款入口、地牢结算、助手索引、设置序列化和存档迁移。无文本冲突也不能视为兼容验证成功。
4. 跑下述定向回归与已有项目检查；从复制的旧档做真实加载测试，禁止拿唯一真实存档当测试夹具。
5. 两端验收通过后再部署、打包和升级。发布过程不覆盖 `.env`、Worker Secret、用户本机数据或 GitHub 存档仓库。

不维护第二套 `Update.ts` 上游迁移表；自用配置迁移与官方迁移分离。未来官方实现同类功能时，明确迁移到官方能力并删除重复模块，而非让两个调度器同时生效。

## 10. 实施前应具备的验收用例

### 价格

- 开关关闭时，新旧档价格、单买、批量、封顶和 Max 与当前代码一致。
- 已有 8 倍／100 倍价格的档，开启后报价和扣款都是基础价；倍率 JSON 不被清零。
- 普通道具、普通精灵球、维生素、钥石、六币种大师球均覆盖；不动非 Item 兑换商店。
- 固定模式购买与战斗后旧倍率保持不变；切回官方模式按旧倍率继续。
- 固定价大量买大师球不写出 Infinity／NaN；钱包扣款与商品数量都在安全范围内。
- 商店打开期间切换模式、重新打开商店、切换临时商品实例均刷新正确。
- 固定价买维生素后退款码被阻止，切模式／刷新／云恢复不能绕开；没有该历史的官方模式档维持原行为。
- 维生素兑换、奖励、失败购买不误设标记；退款确认框等待期间发生固定价购买，确认后也不能扣道具或返钱。

### 地牢

- 1 次、10 次、预算不足、失败、取消、锁定地牢等路径次数与收费一致；不保证成功次数。
- 原批量模式仍有原折扣；增强模式每局按单次费用与门票扣一次，停止后不预收后续费用。
- 结束事件重复触发、异步确认晚返回、快速双击开始，都不能重复开局、扣款或增加统计。
- Boss／训练师捕获回调晚于地牢超时：保持原胜负判定，合法捕获最多结算一次；使用原对象、球种、概率和存档身份，旧局回调不能修改新局敌人、推进新局或再次发通关奖励。
- 多层地图、空路径、不可达目标、敌人阻挡、捕获等待、剩余时间不足均可解释地结束或等待。
- 首通奖励、任务进度、掉落和捕获仍走原路径，无重复结算。
- 手动 Fire、刷新、换城、换档、退出、恢复云档、同步后切设备，均不会遗留自动续局；等待捕获期间不能从其他入口另开地牢。

### 存档和发布

- 当前官方基线 `.txt` 导入新定制端默认官方模式；备份可读。
- 新定制网页 → 新 EXE → 新网页，配置和进度一致，执行中的连刷不恢复。
- 更高 gameVersion 或未知 private schema 正确阻止加载／覆盖；同 gameVersion 的旧定制上传被拒绝。
- 复制的存档在同版官方代码加载、保存、导出、再导入，实测核心字段与自用字段各自的保留／丢失，不用“未报错”代替核对。
- 单局中刷新后不自动重开、不重复发奖；本局进度丢失按原行为说明，不声称做到了崩溃后精确续局。
- 运行现有 `cloud:check`、`cloud:build`、`desktop:test`，再用一键脚本生成新 EXE 并做隔离存档运行验收。设计文档本身不需要重新打包游戏。

## 11. 建议实施顺序

| 批次 | 内容 | 交付后可观察结果 |
| --- | --- | --- |
| A | 配置校验／版本保护 + 固定基础价 + 退款保护 | 旧档开启后不涨价，关闭后仍保留旧倍率，旧端不能覆盖新配置 |
| B | 每局支付的有限连刷、失败即停、预算、本局后停止、摘要 | 可明确知道刷了几局、花了多少、为何停止，刷新不丢大量预付款 |
| C | 根据真实失败样例优化探索和寻路缓存 | 在相同规则下减少绕路和超时，以相同地图样本比较 |

每批单独提交、单独验收；正式发布前准备新版网页和 EXE。方案采用集中接入和保留旧字段降低维护成本，但官方未来若重构地牢或道具系统，仍需要人工适配，不能承诺以后更新永远零冲突。
